# 双机器人语音联调验收

本项是语音功能的真实服务验收标准之一：两个独立 Ooptra 实例使用不同 Oopz 账号，
在同一语音频道通过实际音频完成双向 ASR → LLM → TTS 对话，并在限定轮数后停止。
它与 Python 回归测试、类型检查和浏览器检查共同构成验证证据。

## 适用范围

修改语音采集、VAD、模型后端、流式推送、成员身份映射、监听白名单、回合限额、
进退房或多实例运行方式时，按本流程复测受影响路径，并记录本次结果。
纯文档或无关功能变更无需重新调用模型服务。缺少账号、模型服务或测试房间时，
明确记录「未执行真实双机器人验收」及原因，保留验证缺口。

本流程针对级联后端，首个实测组合为阿里 ASR/TTS + DeepSeek。
Gemini Live 服务端回合需要另行验证，本流程的级联限额不约束它。

## 环境与停止条件

| 项目 | 实例 A | 实例 B |
| --- | --- | --- |
| 项目目录、进程 | 独立目录与进程 | 另一独立目录与进程 |
| Oopz 账号 | 账号 A | 不同的账号 B |
| WebUI | `127.0.0.1:3090` | `127.0.0.1:3091` |
| 本地状态 | 自己的配置、私钥、数据库、记忆、日志和浏览器传输 | 同样独立，不复制 A 的账号凭据或身份数据库 |
| 模型密钥 | 从本实例 `.env.local` 或进程环境读取 | 从本实例 `.env.local` 或进程环境读取 |
| 目标房间 | 同一域与语音频道 | 与 A 相同 |

关闭本次不需要的 OneBot 网络监听／反向连接及独立语音 API；特别是实例 B 的 WebUI
使用 3091 时，同端口的独立语音 API 必须关闭或另选端口。
依赖解释器可共用；共用时在联调期间保持依赖版本一致，应用运行状态仍分别存储。

两边设置 `VOICE_AGENT_CONFIG`：

- `enabled=True`，`backend="aliyun_deepseek"`，`reply_probability_percent=100`。
- `cascade_turn_limit=3`：每次进房最多自动接话尝试三次；在模型调用前扣额度，失败、
  空识别和未触发回复也计次。达到上限停止自动输入，当前输出可播放完毕。
- `listen_only_uids=[对方的 Oopz UID]`；音频回调中的 Agora 数字 ID 通过房间身份广播映射。
- `barge_in=False`，`voice_leave_enabled=False`，`voice_volume_enabled=False`；关闭测试域的自动串门。
- 人格要求每次只说一两句，围绕同一话题自然接话。

手动开场白不消耗自动接话额度。重新进房会重置额度，因此测试中不循环重新进房。
测试控制程序另设 **150 秒整场时限**，覆盖进房、等待身份、开场和自动对话；
无论成功、失败、取消还是超时，均进入退房清理。限额与总时限均由程序执行。

## 执行步骤

1. **核对准备状态。** 确认两端使用不同账号、各自持有状态文件、限额已加载，且 Oopz
   已连接。通过各自配置读取 API Token，调用各自 WebUI 上的语音接口。
2. **进同一房间。** 先清理旧会话，再调用两端 `POST /voice/join`，请求体为同一
   `{"area":"<域 ID>","channel":"<频道 ID>"}`。核对两端 `/voice/status` 的房间相同、
   `joined=true`，以及嵌套 `status.cascade_attempts=0`、`status.cascade_turn_limit=3`。
3. **等待身份。** 轮询两端 `GET /voice/members`，各自确认对方成员的 `live=true`，
   再开始播报。进房成功不等于身份广播已到达；过早开场会被白名单过滤。
4. **仅播报一次开场。** 对 A 调用 `POST /voice/speak`，例如
   `{"text":"你好，我周末想去公园散步，你想做什么？"}`。后续接话由真实房间音频驱动。
5. **观察双向接话。** 保存两端自动尝试次数、成功输出次数、识别与回复的对应关系、
   播放完成／失败状态及耗时。确认 B 先回应开场，随后 A、B 交替，各完成三次自动回复。
   `/voice/status` 的累计 `turns` 可能包含历史轮次及开场，应取本轮增量并区分手动输出。
6. **结束并核对。** 等两端最后一次输出实际播放完成，或在异常／整场超时时停止，
   均调用两端 `POST /voice/leave`。随后分别查询 `/voice/status`，以 `joined=false`
   确认退房；接口不可达或退房失败时记录「未确认清理完成」，继续处理清理。

## 通过条件

以下各项全部满足，才能将本次真实双机器人验收标为通过：

| 检查项 | 可核对的证据 |
| --- | --- |
| 实例隔离 | 两个不同账号和独立状态目录；端口无冲突；一端操作未改写另一端账号配置 |
| 双向真实音频 | B 对 A 的开场产生 ASR 与语音回复，A 再对 B 的实际音频产生识别与回复；后续持续接续 |
| 对话完整 | 一次手动开场 + 六次成功自动回复，两端各三次；只有尝试计数达到 3 而没有成功输出不算通过 |
| 内容可理解 | 识别保留对方发言的核心意思，回复接续上下文；记录影响意思的错识别、截断、重复或明显答非所问 |
| 音频完成 | 推送结果与播放完成记录正常，并有对端后续识别佐证；仅 HTTP 成功、文本生成或本地 PCM 文件不足以证明房间收到声音 |
| 有界停止 | 两端自动尝试均不超过 3，无第四次自动模型调用；排队及失败消耗额度、默认不限额、重新进房重置额度的回归测试通过 |
| 清理完成 | 150 秒内完成正常对话，并确认两个实例最终均 `joined=false`；超时终止用于止损，不能算正常验收通过 |

音质人工旁听需要第三个账号，避免占用正在运行的两个机器人账号。
无人旁听时，记录双向识别与播放证据，并将人工音质评价标为「未验证」。
流式首包、打断、重连、旧会话迟到回调等行为仍由对应回归测试或专项实测覆盖。
本项不单独证明端到端延迟达标，也不证明纯 ASR／LLM／TTS 某一服务的性能上限。

## 验收记录与证据保存

每次复测记录：日期与时区、提交及工作区差异、两个实例的版本／配置差异、模型与音色、
轮数／总时限、实际成功回复数与尝试数、耗时、双方退房确认、问题和未验证项。
环境或版本变化后保留新的记录，不将历史通过结果套用到当前改动。

长期保留脱敏结论与必要回放。凭据、原始配置、身份数据库和私人对话留在忽略目录；
验收时需要的音频／正文采集仅用于已授权的测试会话，结束后关闭临时采集并恢复正常入口。
合成回放需标明来源：本流程的回放由实际成功推送的机器人音频与日志字幕合成，
可用于听取输出和追踪内容，不能作为浏览器真实扬声器录音或屏幕录制的证据。
