# 代码审查要求

适用于人工和代理审查。先阅读 [架构地图](../ARCHITECTURE.md) 与 [代码要求](coding-standards.md)，固定审查范围（提交、PR 或明确的工作区 diff），核对本次需求与实际行为。代码要求是规则来源；本文规定如何验证。

## 模块与接口审查

新增模块、迁移文件或修改公开接口时，先按 [目录规则](coding-standards.md#模块目录与接口导航) 完成以下核对：

涉及模块划分、公开接口或状态归属的设计审查，同时使用项目级 [深模块架构设计 skill](../.agents/skills/design-deep-modules/SKILL.md) 中的自查方法，提供调用路径和行为证据。

1. 从架构导航进入模块 README 和公开接口，应能决定修改位置；检查契约的输入、失败、完成与取消语义，以及工厂是否暴露了内部对象。
2. 追踪状态拥有者和跨模块调用，检查私有属性访问、动态导入、循环依赖，以及 `app`、`core` 或兼容适配中是否藏入了业务状态。
3. 检查接口是否隐藏了协调复杂度；仅转发调用、要求调用方手动管理内部锁与代次的层应重新划分。实际流程中的资源与时序约束不能因分层而丢失。
4. 按 [测试导航](../tests/README.md) 核对模块测试与跨模块流程；检查迁移后的发现数量、旧入口移除及兼容适配的剩余范围。

目录检查通过只代表静态规则通过，不代表接口隔离或状态所有权已经完成。

## 输入边界审查

修改 HTTP、模型工具参数、配置或持久化恢复路径时，逐条完成以下追踪：

1. **找输入与副作用。** 列出变更涉及的外部输入、解析入口和最终动作；确认输入完成解析后才进入写配置、进退房、发音频等副作用。
2. **查保留信息。** 对每个入口写出 `原始输入 → 解析函数 → 返回类型 → 消费方`。确认后续使用返回对象；检查调用后忽略结果、只返回合法与否、重新读取 raw、转回无类型字典或重复读取字段的路径。
3. **查构造不变量。** 核实直接构造是否能制造未知动作、越界数值、缺少必需字段或互斥组合；检查对象是否会被原始输入的后续修改污染。只添加类型名称或冻结对象不足以证明约束成立。
4. **查绕过与边界。** 逐处检查新增的 `Any`、`cast`、`type: ignore`、`pyright: ignore`、`noqa`；核对其证明依据。JSON 序列化和旧协议兼容处可恢复为字典，但新业务接口应保留领域类型。动态的认证、房间归属、权限与代次会变化，执行前仍须复查。
5. **查失败与证据。** 验证非法输入在副作用前失败，合法空值与解析失败有区别。检查边界值、构造绕过、调用方消费及既有协议兼容测试；核对 Ruff、Pyright 和相关测试的实际结果。

审查结束时，每个变更入口都应有完整追踪，或明确标注不涉及输入解析。已有代码无需借一次局部变更迁移全库；新增的未类型化业务通路、原始输入继续泄漏或未经证明的类型断言应作为具体问题提出。

## 日志审查

修改日志、异常处理或异步生命周期时，按 [日志要求](coding-standards.md#日志与可观测性) 逐路径核对：

1. 从一次实际操作追踪开始与终态，确认请求、回合、房间和代次取自同一任务上下文；复查迟到任务是否被错误归到新会话。
2. 检查级别与重试汇总，确认最终失败有堆栈和唯一记录责任方，取消、打断及过期丢弃能区分；检查后台任务异常是否被观测。
3. 检查消息、参数及异常文本中的敏感数据、外部换行和超长正文；用合成凭据验证脱敏，确认必要字段在实际输出中可见，仅传 `extra` 不代表已输出。
4. 修改 handler、队列或采集器时，验证重复初始化、队列满、退出、轮转、WebUI 兼容及实例隔离；列出实际验证结果和未覆盖的故障。普通业务日志无需运行无关的基础设施测试。

完成时应能用同一操作的日志解释其结果，并指出尚缺的证据；仅 lint 通过不足以证明满足日志要求。

## 报告格式

每个问题提供代码位置、触发输入、丢失的信息或可构造的非法状态、实际影响与修复方向。区分以下结果：

- **明确缺陷**：可以给出导致错误行为或绕过边界的输入与执行路径。
- **设计改进**：类型表达较弱，但未发现错误路径；说明收益与迁移范围，不将其自动视为阻塞问题。
- **验证缺口**：缺少能证明关键不变量或兼容路径的测试，列出需要补充的场景。

报告单独说明需求符合情况与代码要求符合情况；工具已发现的诊断只汇总状态，重点解释工具无法判断的问题。PR 使用 [仓库模板](../.github/pull_request_template.md)，记录解析通路、兼容边界和实际验证结果。
