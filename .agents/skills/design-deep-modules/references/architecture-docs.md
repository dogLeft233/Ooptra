# 架构文档维护与验证

用于编写、拆分、维护或审查 Ooptra 架构文档。目标是让人和 Agent 从系统总图找到所属模块、使用契约及验证入口，并独立完成局部修改。沿用现有文档位置；每项事实只有一个权威位置，上层通过链接导航。

## 分层与事实归属

| 位置 | 负责描述 | 不在这里重复维护 |
| --- | --- | --- |
| 根 `ARCHITECTURE.md` | 系统边界、五模块职责、跨模块主流程、全局不变量、权威状态归属、模块导航及必要的迁移差距 | 内部文件清单、完整接口签名、详细迁移进度 |
| `src/<模块>/README.md` | 职责与非职责、接口入口、内部能力地图、局部状态与生命周期、依赖、测试入口 | 全系统说明、已实现接口的第二份参数清单 |
| 必要的子模块 `README.md` | 可独立维护的内部能力、隐藏的知识、内部接口入口、状态与局部约束 | 所有父层规则及每个文件的解释 |
| 接口代码、公开类型与 docstring | 类型、前置条件、效果、结果、失败、顺序、完成及取消语义 | 整体架构地图与设计历史 |
| 现有 `docs/superpowers/specs/` | 重要设计问题、备选方案、取舍、决定与后果 | 当前实现的竞争性地图 |
| 现有 `docs/superpowers/plans/` | 迁移步骤、进度、验证与剩余工作 | 长期有效的当前架构规范 |

跨模块约束由根文档定义，局部文档链接引用并说明局部应用。例如“生成完成不等于播放完成”属于跨模块契约，模型连接如何重建属于对话生成内部。

文档与代码不一致时，明确标记已实现、目标设计、迁移差距及核实范围，保留冲突证据。草案可描述未来接口，但必须标记未实现；接口落地后以代码契约为准，将重复签名改为导航。不能用目标文档覆盖实际偏差，也不能把违规实现自动改写为允许的设计。

只有存在可独立理解的职责或状态、内部边界及实际维护需求时，才增加子模块说明。简单辅助函数和适配器使用代码及 docstring 即可。不按文件夹机械建文档，不设强制文档深度或字数；子模块文档不自动授予新的跨大模块访问权限。

## 模块说明模板

按复杂度省略不适用项，不要求为模板创建空目录或空文件：

```markdown
# 模块名称

## 职责与边界
解决的问题；相邻职责归谁；调用者无需掌握的知识。

## 状态与实现程度
已实现、部分迁移或设计中；当前入口及未落实的边界。

## 使用入口
公开接口和类型的位置；调用示例或示例入口。
必要的非类型约束链接至契约定义。

## 内部地图
按子能力列出职责、隐藏的知识及实现或文档入口。

## 状态与生命周期
权威状态拥有者、允许的修改入口；启动、关闭、取消及故障收尾。

## 依赖与禁止访问
允许的静态依赖及运行时协作方式；不得跨越的内部边界。

## 验证入口
测试位置、运行命令、关键行为场景和已知验证缺口。
```

## 变更触发与同步

| 变更 | 同一变更中维护的位置 |
| --- | --- |
| 算法或内部组织改变，契约及架构断言不变 | 代码与适用测试；通常无需更新架构文档 |
| 子模块职责、状态归属或内部边界变化 | 所属模块及受影响子模块说明 |
| 公开接口变化 | 接口代码与测试；模块文档中的使用说明与指针；跨模块语义改变时更新根文档 |
| 五模块职责、跨模块流程或全局不变量变化 | 根文档及受影响模块说明 |
| 新增、移动或删除文档、接口、测试入口 | 修正所有受影响的导航；新增或移动文档按仓库要求同步 AGENTS 索引 |
| 重要设计决定或迁移推进 | 相应设计记录或计划，并同步已发生变化的架构断言 |

修改边界的人负责同步文档，代码审查核对维护范围。保留既有人工说明和无关改动；不为每次提交刷新时间戳，不为普通局部修复新建设计报告或启动全库重写。完成迁移后移除失效入口和过渡说明，历史原因留在设计记录中。

## 文档验证方法

对本次受影响的断言逐项核查，报告实际范围；文档审查不要求遍历全库。

| 检查 | 执行方法与完成条件 |
| --- | --- |
| 导航可达 | 从根架构沿模块导航到公开接口、必要子模块及测试入口；目标存在，草案明确标记。沿实际链接走一遍，不能只确认文件名出现过 |
| 链接与入口 | 检查新增或修改链接的相对路径和锚点；核对提及的代码符号、目录、测试命令。已有命令与配置可静态核对，不为检查文档执行未知脚本 |
| 事实一致 | 为职责、状态拥有者和关键流程找到接口、调用路径、配置或测试证据；纯设计约束给出设计依据。未知项标未知，缺少反例不等于全局保证 |
| 契约可用 | 只读模块说明和公开契约，写出真实调用及适用的失败、取消处理；记录必须追问的隐含步骤，补齐契约或重划边界 |
| 单一事实来源 | 逐项检查接口清单、状态归属和规则是否多处复制；保留一个定义，其余改为引用。全局原则与局部应用可以并存，但须一致 |
| 层级合适 | 上层足以选择下一个模块；局部说明足以定位实现和验证。删去逐文件罗列与无价值层级，避免为文档整齐拆代码 |
| 图文一致 | 核对图中的箭头含义、范围与正文；分别表达运行时事件流和静态依赖，不从反馈箭头推导循环导入许可 |

对新增或明显改变的边界，再补一条变化场景：记录触发变化、预期影响范围、实际涉及的接口和调用者、发现的泄漏。可从“更换生成供应商”“调整主动发言冷却”“更换记忆存储”选取本次相关场景。必要时做小规模实现验证；仅推演时标记为设计分析。

## 验证结论的边界

- 文档检查证明导航、断言和契约说明在本次范围内一致，不能证明运行实现正确。
- 现有 `scripts/check_architecture.py` 检查目录和部分静态导入；它不能证明状态唯一归属、动态访问、接口易用或模块划分合理。按需运行并报告结果，不把本参考页中的检查描述为已配置的自动检查。
- 代码边界变更按 skill 正文执行公开行为、变化影响及适用的故障序列验证，并遵守仓库测试要求。纯文档变更核对链接、契约、差异即可，无需启动无关运行验收。
- 交付说明列出维护位置、证据范围、已检查项、未实现契约及未验证路径。保留静态检查、纸面分析、自动行为测试、真实联调之间的区别。
