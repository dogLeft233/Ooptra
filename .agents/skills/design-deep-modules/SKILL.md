# 设计可独立理解的深模块

目标：让人和 Agent 通过模块职责与公开接口选择工作范围，在不理解其他模块实现的前提下完成局部修改，并获得可靠反馈。深度指接口提供的能力和隐藏的复杂度，不按目录层数、文件长度或实现行数衡量。

先读 [系统架构](../../../ARCHITECTURE.md)，确认目标与当前实现的差距；目录约束以 [代码要求](../../../docs/coding-standards.md#模块目录与接口导航) 为准，测试归属见 [测试导航](../../../tests/README.md)。本 skill 规定设计与自查方法，不另建一份架构地图。

编写、拆分、维护或审查架构文档时，读取 [架构文档维护与验证](references/architecture-docs.md)，按其中的分层职责、变更触发规则和验证清单执行。设计改变边界时，同一变更同步对应文档；内部实现变化且契约不变时，无需逐层改文档。

## 设计目标

- **信息隐藏**：每个模块集中拥有一组相关知识、设计决策与状态，调用者仅了解使用它所必需的信息。
- **接口有用且易用**：常用任务通过少量明确操作完成。接口包括类型、效果、失败、顺序、完成与取消语义；调用方不必翻实现才能正确使用。
- **修改局部化**：保持契约不变时，内部算法、存储或供应商变化不会迫使多个调用者一起修改。
- **渐进阅读与验证**：职责导航 → 公开接口及类型 → 按需阅读实现；接口行为测试给出快速、可重复的反馈。

## 架构设计时不要做什么

| 禁止的做法或需纠正的信号 | 应采取的设计动作 |
| --- | --- |
| 为了整齐或追求短文件，机械增加类、目录、基类及层级 | 说明该抽象隐藏了什么知识、替调用者解决了什么问题；没有实际收益就合并或省去 |
| 新层逐个转发下一层同名方法，调用者仍须理解整条调用链 | 把重复协调收敛为有意义的任务；确有协议转换或兼容价值的薄适配可保留并说明用途 |
| 仅按“读取 → 处理 → 写入”的执行顺序拆模块，使多个模块都理解同一格式或规则 | 按知识与变化原因重新聚合；流程步骤可作为内部函数，不必都成为公开模块 |
| 用下划线、私有字段或 `api.py` 外壳声称封装完成，却让调用者拿到 SDK、内部对象或可变状态 | 通过命令、具名结果和只读快照提供能力；检查工厂返回对象是否形成后门 |
| 让调用者自行拼装内部锁、执行代次、重试、清理与调用顺序 | 将模块能可靠处理的协调下沉；保留确实需要调用者决策的领域失败，不吞错或无限重试 |
| 用通用字典、布尔开关或任意回调缩短接口，把复杂度交给调用者 | 使用能表达有效状态的类型和操作；解释真实约束，避免每个调用者重新验证同一事实 |
| 为假想的供应商、插件体系或未来需求预建扩展框架 | 覆盖当前真实用例，提取已有共同语义；有明确变化需求时再增加机制 |
| 将复杂协调搬到 `app`、`core` 或万能上下文对象，制造表面简单的业务模块 | 明确唯一状态拥有者与业务判断归属；装配只协调流程，共享机制不承担业务策略 |
| 用目录移动、文档数量、lint 通过或测试数量宣称架构改善 | 用实际调用路径、变更影响范围和行为证据证明收益；目标契约必须标记未实现部分 |
| 以抽象统一为由抹平模型与协议的实际能力差异 | 对共同任务抽象，显式表达能力差异；例如保留实时语音与级联生成各自所需的流语义 |

这些限制用于约束本次设计，不授权顺带重构全库。发现历史问题时，先判断其是否阻碍当前任务；不阻碍则记录位置与影响，避免扩大变更。

## 设计与自查方法

### 先证明需要怎样的模块

选一条真实路径，查看调用者、实现与相关测试；按仓库指南优先使用 Codegraph，结果不足时用定向搜索核实。记录：

`当前调用者 → 当前需掌握的知识 → 拟保留的接口 → 迁入内部的知识 → 状态拥有者`

用一句话说明模块的独特能力。若描述只能是“调用下一个对象”，重新判断该模块是否必要。

对新增或明显改动的边界，简要比较两种可行方案，例如保留在同一模块与拆分、任务式接口与多步接口。按调用者负担、信息泄漏、状态归属和迁移成本选择；普通内部修复不强制写方案。

选取本次边界相关的变化场景，先预测影响范围，再用调用路径分析或小规模实现核对。例如更换共同能力不变的生成供应商，应主要影响对话生成；调整主动发言冷却，应主要影响行为决策。记录实际扩散位置，区分需求改变共同契约与内部知识泄漏；纸面推演只提供设计证据，不作为实现验证通过的结论。

### 用具体反例检验接口

| 自查 | 所需证据；失败时的处理 |
| --- | --- |
| **只读接口测试**：不读 `_internal/`，能否写出一个真实调用？ | 给出调用示例，含合法输入、结果、失败与必要的取消处理；若必须查锁或隐藏调用顺序，补契约或重划职责 |
| **信息泄漏测试**：有哪些规则同时被多个模块掌握？ | 追踪数据格式、供应商参数、可变状态及实际调用；将重复知识集中到拥有者，不能只检查 import |
| **替换测试**：内部算法、存储或后端改变，哪些调用者必须改？ | 列出应保持不变的调用位置与测试；真实能力变化可修改契约，纯实现变化不应传播 |
| **去层测试**：移除这一层，它处理的复杂度会去哪？ | 若同样代码被迫散落多个调用者，说明有封装价值；若只减少转发且不丢语义，考虑合并 |
| **故障测试**：外部失败、取消、重复或迟到结果由谁收尾？ | 按风险选择适用场景，明确状态拥有者、终态及资源回收责任；不能让多个模块各自猜测真实状态 |
| **导航测试**：从顶层能否找到接口和相关验证命令？ | 实际沿架构导航到模块和测试入口；修复失效指针，避免多处复制接口清单 |

Ooptra 的故障检查尤其关注：生成完成与播放完成不同；切房后旧输出不得操作新会话；外部记忆回执与生成结果不同；AstrBot 与本地能力不能重复响应同一事件。仅在本次路径涉及时展开验证。

### 按风险验证，报告实际完成程度

- 先运行 `python scripts/check_architecture.py`：它检查目录和部分静态导入，不能证明动态访问、状态归属、模块深度或依赖方向正确。
- 通过公开接口验证可观察行为；内部测试可覆盖重要算法，但不能仅靠 mock 调用次数、私有字段断言或逐层重复测试证明封装。
- 多实现的共同契约可运行同一套行为测试，特有能力单独验证；异步接口按风险检查切房、取消、迟到输出与重复回执的操作序列，必要时使用状态机测试，无需为简单接口引入新框架。
- 分别描述运行时事件流与静态导入方向。反馈流程不意味着具体实现可以循环导入；通过装配和注入连接模块。新增静态规则前先明确允许的依赖，检查器通过不证明规则本身合理。
- 代码变更按仓库要求执行相关测试、Ruff、Pyright 和提交前完整检查；接口迁移还需核对调用者、旧入口与测试发现。纯设计文档变更检查链接和契约一致性，不启动无关运行验收。
- 对故障行为使用隔离 fixture 和可控失败，记录实际结果及未验证路径；已有测试通过不等于新契约已覆盖。

输出随任务规模简述：**目标与现状；选择及取舍；隐藏的知识与保留的接口；唯一状态拥有者；调用者迁移范围；验证证据及缺口**。已有设计或 PR 中补充即可，不为每次修改新建报告。代码审查时按 [审查要求](../../../docs/code-review.md) 把问题落实到位置、路径和影响。

## 来源与适用边界

- [Matt Pocock：How To Make Codebases AI Agents Love](https://www.aihero.dev/how-to-make-codebases-ai-agents-love)：深模块、渐进披露、行为测试与反馈，有助于降低人和 Agent 理解代码的成本。
- [John Ousterhout：CS 190 Modular Design](https://web.stanford.edu/~ouster/cgi-bin/cs190-winter18/lecture.php?topic=modularDesign)：接口包含使用约束；信息隐藏、避免时序拆分与透传层、适度通用化，并通过比较设计改进抽象。
