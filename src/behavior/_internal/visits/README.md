# 串门与调度

现有串门实现已迁入本模块，入口为 `create_auto_visits/create_visit_store` 及 [公开 AutoVisits/VisitsHost](../../api.py)。本能力拥有候选房间、日额度、耐久访问预留、问候/告别阶段、手动覆盖、独处退出、定时器与有限重试。

## 深任务接口的选择

保留异步任务作为该深模块的实现：应用交付配置、手动操作和就绪通知，再通过 start/stop/pause/resume 管理任务。模块通过注入的 `VisitsHost` 请求必要的目录查询、进退房、公告和回复等待；实际房间仍由渠道确认，实际表达仍由生成/渠道执行。这里没有 SDK、整个 VoiceCoordinator 配置或模型句柄。

此前草案的 `advance/settle/next_wakeup` 纯意图循环未采用。它会把问候→停留→等待回复→告别→有限退房重试的驱动顺序暴露给应用，使应用必须理解串门阶段。当前接口把这些知识集中在服务中，执行能力由窄端口授权；这不是缺少迁移，也不要求所有行为都机械实现同名 decide。

## 访问与持久化

`AutoVisitConfig` 递归冻结台词和字典；`effective_area` 返回独立快照，配置变更重新解析并 reload，提升查询代次。计划、冷却与持久访问状态只有此模块持有，不复制当前真实房间。

访问先耐久 reserve，真实进房成功后 confirm；只有执行端口同时报告 `room_state=idle` 和 `room_cleanup_pending=False`，才允许确定失败后 rollback。未知进房、旧账号传输未清理或字段缺失均保留预留并暂停。重启发现 pending 不能清零猜额度，持久化失败不以空计数继续运行。

额度沿用原北京时间日切和冷却持久化。人工退房与自动退房采用各自既有冷却；手动控制提升代次，旧候选/问候/告别不能操作新房间。查询后、预留后、执行前复查原目录绑定/操作代次；真实房间另由渠道执行复查。

## 内部阶段与退出

内部活跃访问依次经历预留、进房、问候、停留、等待当前回复、告别和退房。状态是服务内部知识，不作为应用分支条件。进入退出阶段先停止新自动回合，有限等待当前回复，再按原规则告别/退房；有限退房重试保持既有0/2/5秒节奏，渠道不另加一层业务重试。

独处退出同样适用于已观察人工房间；只有可信成员状态持续满足原30秒窗口才退出，未知成员/查询失败重置窗口。停止任务回收定时器和访问任务，不擅自退出人工房间；未确认的耐久访问保留供恢复核对。

主动开启新话题是独立产品扩展，本次重构不新增。现有自动串门和问候均按原配置运作，不称为自主聊天，不留无调用者的话题策略或未来插件框架。

## 验证与变化范围

`tests/behavior/test_visit_service.py` 验证配置不可变、人工退房冷却重启恢复、未知进房与旧传输保留预留；`tests/test_auto_visit_controller.py/test_auto_visit_state.py/test_auto_visit_integration.py/test_empty_room_status.py` 保留访问阶段、日额度、手动优先、有限重试和独处规则回归。存储和执行端口可注入；目录与实际渠道状态使用临时替代外部服务验证，不读/改生产数据。

调整候选或告别政策应主要改本目录；替换传输不改串门规则。模块不导入 replies，接话策略也不读取本模块私有 phase。共享的是公开的通知和必要准入语义，避免重复状态表。
